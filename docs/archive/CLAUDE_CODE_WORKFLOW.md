# Claude Code 활용 과정

이 프로젝트는 처음부터 끝까지 **Claude Code CLI 환경에서 자연어 대화로 지시**하며 진행했다. 이 문서는 "AI가 대신 분석했다"가 아니라, **사용자가 Claude Code를 도구로 활용해 데이터 분석 워크플로우 전체를 설계·검증·수정해 나간 과정**을 보여주기 위해 작성했다. 이 README와 리포트, 그리고 지금 읽고 있는 이 문서 자체도 Claude Code로 작성했다.

## 1. 작업 환경을 먼저 구조화

분석을 시작하기 전에 Claude Code에게 프로젝트 구조 설계를 지시했다.

- `CLAUDE.md`(프로젝트 개요·환경·데이터 스펙)를 작성해, 이후 모든 세션에서 Claude Code가 프로젝트 맥락을 즉시 파악하도록 했다.
- `data/`(원본 데이터, 읽기 전용) / `scripts/`(분석 코드) / `output/`(결과물) / `worklogs/`(작업 기록)로 폴더를 분리하도록 지시했다.
- 스크립트 파일명을 "결과물과 매칭되는 이름 + 순번"(`01_temp_vs_cnt_scatter.py`처럼)으로 저장하는 규칙을 세워, 코드와 산출물의 대응 관계를 누구나 추적할 수 있게 했다.
- **작업로그 규칙**을 설계했다: `worklogs/worklogs.md` 최상단에 "현재 상태" 블록(진행 중인 작업/완료됨/막힌 것/다음 할 일/결론)을 두고, 매 작업 후 이 블록을 최신화하도록 CLAUDE.md에 명시했다. 이 덕분에 세션이 끊겨도 상단 블록만 읽으면 바로 이어서 작업할 수 있었다.

## 2. 데이터를 "읽기 전용"으로 먼저 검증

데이터를 임의로 수정하지 않고, 구조·타입·결측치·중복·이상치를 먼저 확인하도록 지시했다. Claude Code는 pandas로 결측치 0건, 중복 0건을 확인하고, IQR 기준 이상치 탐지에서 `hum=0`(2011-03-10)처럼 물리적으로 비정상적인 값을 스스로 찾아내 보고했다. 이 값은 원인이 불확실해 임의로 보정하지 않고 **한계점으로 명시**하는 방향으로 판단을 조율했다.

## 3. 피드백을 반영해 시각화를 즉시 재구성

`season`, `weekday` 각각의 박스플롯을 만든 뒤, "따로가 아니라 계절×요일 **조합**의 경향을 보고 싶다"는 피드백을 주자 Claude Code가 곧바로 피벗 테이블 기반 히트맵으로 다시 그렸고, 이제 불필요해진 개별 박스플롯 파일은 삭제했다. 시각화 도구를 한 번에 확정하지 않고, 실제로 보고 판단한 뒤 방향을 바꾸는 반복 루프로 진행했다.

## 4. 렌더링 버그를 직접 재현·수정

4개 모델 비교 막대그래프 작업 중, matplotlib + 맑은 고딕 조합에서 "낮을수록"이라는 라벨의 특정 글자가 작은 폰트 크기에서 깨지는 렌더링 버그를 발견했다. 원인을 폰트 렌더링 이슈로 특정한 뒤, 같은 의미의 다른 표현("작을수록")으로 바꿔 해결했다 — 코드 로직이 아니라 **폰트/렌더링 레벨의 실전 버그를 진단하고 우회한 사례**다.

## 5. 데이터 누수를 실험으로 검증

선형회귀 모델에 `casual`/`registered`를 입력으로 포함했을 때 RMSE≈0, R²=1.0이라는 비정상적으로 완벽한 결과가 나왔다. 이를 그대로 "좋은 모델"로 보고하지 않고, `cnt = casual + registered`라는 정의상 항등식 때문에 발생한 **데이터 누수**임을 회귀계수(`casual=1.0`, `registered=1.0`, 나머지 0)로 직접 확인했다. 이후 모든 모델에서 두 변수를 제외하도록 기준을 통일하고, 새는 결과와 실질 결과를 리포트에 둘 다 남겨 무엇이 왜 잘못됐는지 추적 가능하게 했다.

## 6. 모델을 단계적으로 확장하며 공정하게 비교

선형회귀 → 랜덤포레스트 → XGBoost → XGBoost(튜닝) 순으로, 매번 이전 모델과 **동일한 입력 변수·동일한 train/test 분할(random_state=42)**을 유지하도록 지시해 비교 가능성을 확보했다. XGBoost 튜닝은 `GridSearchCV`로 108개 하이퍼파라미터 조합을 5-fold 교차검증했다. 최종적으로 RMSE·MAE·R² 세 지표의 순위를 각각 매기고 평균 순위로 종합했는데, MAE 기준으로는 랜덤포레스트가 더 낫다는 사실도 숨기지 않고 그대로 리포트에 남겨 **단일 지표로 우열을 단정하지 않는** 방향으로 정리했다.

## 7. 작업 전 과정을 계속 문서화

각 단계가 끝날 때마다 별도 요청 없이 작업로그를 갱신하도록 진행했다. 그 결과 어떤 분석을 왜 했는지, 어떤 판단(예: `season` 코드가 실제 계절과 어긋난다는 것을 `mnth`와 교차 대조해 발견한 것)을 근거로 다음 단계를 결정했는지가 시간순으로 남아 있다. 이 저장소의 [`docs/REPORT.md`](REPORT.md)와 [`../README.md`](../README.md)는 그 작업로그와 실제 산출물(`output/`)을 근거로 재구성한 문서이며, 수치·해석을 새로 지어내지 않았다.

## 8. 기존 파이프라인을 건드리지 않고 새 질문을 열어 심화 분석

핵심 모델링(선형회귀~XGBoost 튜닝, 스크립트 01~10)을 마친 뒤에도 "IsolationForest로 이상한 날을 찾아달라"는 새 요청을 받았다. 처음엔 "찾기만 해줘, 해석은 하지 마"라는 제약을 걸어 탐지 결과 자체만 먼저 확인했고, 이후 "가장 이상한 5개만", "원인이 되는 변수는", "시각화로", "output에 정식 반영"까지 대화를 이어가며 단계적으로 범위를 넓혔다. 매 단계 이전 결과(37일 목록, leave-one-out 원인 변수)를 다음 질문의 입력으로 그대로 재사용해, 분석이 누적되도록 진행했다.

## 9. 판정 방식을 스스로 의심하고 더 엄밀한 방법으로 교체

이상치 원인을 처음엔 "전체 분포 대비 표준편차(z-score)가 큰 변수"로 설명했다. 그런데 "가장 직접적인 원인이 무엇인지" 다시 묻자, z-score는 변수 하나만 보기 때문에 변수 간 상호작용(예: 강풍과 고습이 동시에 나타나는 날)을 설명하지 못한다고 판단해, 변수를 하나씩 제거하고 모델을 다시 학습해 이상 순위가 얼마나 정상 쪽으로 이동하는지 측정하는 **leave-one-out 기여도 분석**으로 교체했다. 그 결과 37일 중 21일(57%)의 직접 원인이 `weathersit`(날씨등급)로 나왔는데, 이 변수가 전체의 2.9%(21/731)뿐인 희귀 범주라서 Isolation Forest 구조상 과대 대표될 수 있다는 한계도 결과와 함께 기록했다.

## 10. 데이터 안의 결론을 외부 사실과 대조해 검증

상위 5개 이상일에 대해 "원인을 외부 검색해서 근거와 함께 제시해달라"는 요청을 받고, 데이터의 정규화 공식(`temp = (t+8)/47` 등)을 역산해 물리 단위(°C, km/h)로 복원한 뒤 NOAA NCEI(워싱턴 레이건 국립공항 관측소)의 실제 관측 기록과 대조했다. 복원값과 실측값이 기온 1.4°C, 풍속 1km/h 이내로 일치해 역정규화 자체가 정확함을 먼저 확인한 다음, 4일은 실제 기상 이벤트(2011년 1월 폭설로 인한 퇴근길 마비, 할로윈 노리스터, 2012년 말 겨울폭풍, 국가 크리스마스트리를 쓰러뜨린 강풍)로 확인했다. 나머지 1일(2011-03-10, 습도 0%)은 외부 기록상 실제로는 비가 온 날이었다는 게 드러나, "기상 이벤트"가 아니라 **데이터 자체의 결측·센서 오류**로 결론을 바꿨다 — 시간별 원본 데이터를 다시 대조해 그날 22시간 전부 습도 0으로 기록된 것을 확인함으로써 추측이 아니라 데이터로 뒷받침했다.

## 11. 서로 다른 두 지표를 섞지 않고 각각 검증

최고 성능 모델(XGBoost 튜닝)로 731일 전체를 예측해 가장 크게 틀린 10일을 뽑자, 이상치 37일과 겹치는 건 1일뿐이었다. "그럼 모델 성능이 부족한 거 아니냐"는 질문에 두 지표가 애초에 다른 것을 잰다는 점(이상치=입력의 통계적 희귀성, 예측오차=특정 모델의 실패)을 근거로 설명하면서도, "그래도 완전히 무관하지는 않다"는 것 역시 데이터로 다시 확인했다. 그룹별 상대오차(MAE/평균cnt)를 추가로 계산해 이상치 날의 오차가 평범한 날의 3.5배(21.2% vs 6.0%)라는 걸 보여, "개념은 다르지만 이상치가 확실히 더 어려운 날인 것도 맞다"는 절충된 결론을 수치로 뒷받침했다.

## 12. 합계 지표 하나만 보고 결론 내리지 않기

"휴일이 대여량에 영향을 미치나"라는 질문에 전체(cnt) 평균만 비교했다면 p=0.06으로 "효과 없음"이라 결론 났을 것이다. 회원(registered)/비회원(casual)으로 나눠 유의성 검정을 다시 하자 둘 다 p<0.05로 뚜렷했고, 방향이 정반대(회원 −33%, 비회원 +76%)라서 합계에서 서로 상쇄되고 있었다는 게 드러났다. 합계 지표 하나만 보고 "유의하지 않다"고 단정하지 않고, 구성 요소를 나눠 재검증하는 방향으로 분석을 심화시켰다.
